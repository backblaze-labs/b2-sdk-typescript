# Harness Engineering — Reference Notes

> Structured reference distilled from **"Harness engineering: leveraging Codex in an
> agent-first world"** by **Ryan Lopopolo** (OpenAI), Feb 11, 2026 —
> <https://openai.com/index/harness-engineering/>. These are working notes/summary in my own
> words with a few short quotes; consult the original for the full text.
>
> Scope note: the first two sections summarize the article. The final implementation section is
> an adaptation for other projects; items labeled **Adaptation** are useful extrapolations, not
> direct claims from the article.

## The experiment (thesis)

- For ~5 months a small team built and shipped an internal beta software product with **0 lines
  of manually-written code** — application logic, tests, CI, docs, observability, and internal
  tooling all written by **Codex**. The product had internal daily users and external alpha
  testers, and was estimated at **~1/10th** the time of hand-writing it.
- **"Humans steer. Agents execute."** The constraint was chosen deliberately to force building
  what's needed to raise velocity by orders of magnitude.
- Scale: ~1M LOC, ~1,500 PRs, **3 → 7 engineers**, **~3.5 PRs/engineer/day** — throughput
  *rose* as the team grew. Not output for its own sake: hundreds of internal users, daily power
  users. Core philosophy: **no manually-written code**.
- The real question: what changes when an engineering team's primary job is no longer to write
  code, but to **design environments, specify intent, and build feedback loops**.

## The eleven sections

### 1. We started with an empty git repository
- First commit ~late Aug 2025. The initial scaffold (repo structure, CI, formatting, package
  manager, framework) was generated by **Codex CLI + GPT‑5** from small templates.
- **Even `AGENTS.md` was written by Codex.** No pre-existing human code anchored the system —
  the repo was shaped by the agent from the start.

### 2. Redefining the role of the engineer
- Engineering work shifts to **systems, scaffolding, and leverage**.
- Early progress was slow because the **environment was underspecified**, not because the agent
  was incapable — it lacked tools, abstractions, and structure.
- Work **depth-first**: break big goals into small building blocks (design, code, review, test),
  have the agent build them, then compose them into harder tasks.
- When something fails, the fix is **never "try harder."** Ask: **"what capability is missing,
  and how do we make it both legible and enforceable for the agent?"**
- Humans interact almost entirely through **prompts**. To drive a PR: Codex reviews its own
  diff locally, requests further agent reviews (local + cloud), responds to feedback, and loops
  until reviewers are satisfied (a "Ralph Wiggum Loop"). Codex uses standard tools directly
  (`gh`, local scripts, repo-embedded **skills**). Human review is optional; most review is
  **agent-to-agent**.

### 3. Increasing application legibility
- The bottleneck became **human QA capacity**, so they made the app itself legible to Codex.
- App made **bootable per git worktree** → the agent launches/drives one instance per change.
- **Chrome DevTools Protocol** wired into the agent runtime; skills for DOM snapshots,
  screenshots, navigation → the agent can **reproduce bugs, validate fixes, reason about UI**.
- **Observability** exposed per-worktree (ephemeral): query logs with **LogQL**, metrics with
  **PromQL**. Makes prompts like *"startup < 800ms"* or *"no span in these journeys exceeds 2s"*
  tractable. Single runs sometimes work **6+ hours** (often overnight).

### 4. Repository knowledge as the system of record
- Context is the scarce resource. **"Give Codex a map, not a 1,000-page instruction manual."**
- **One giant `AGENTS.md` fails predictably:**
  1. **Context is scarce** — a huge file crowds out the task, code, and relevant docs.
  2. **Too much guidance becomes non-guidance** — when everything is important, nothing is;
     agents pattern-match locally instead of navigating intentionally.
  3. **It rots instantly** — a monolith becomes a graveyard of stale rules; an *attractive
     nuisance* nobody maintains.
  4. **It's hard to verify** — a single blob doesn't lend itself to mechanical checks
     (coverage, freshness, ownership, cross-links), so drift is inevitable.
- So `AGENTS.md` is the **table of contents (~100 lines)**, injected as a map with pointers; the
  real knowledge base lives in a structured **`docs/`** dir treated as the **system of record**.
- The published layout:

  ```text
  AGENTS.md
  ARCHITECTURE.md
  docs/
  ├── design-docs/
  │   ├── index.md
  │   ├── core-beliefs.md
  │   └── ...
  ├── exec-plans/
  │   ├── active/
  │   ├── completed/
  │   └── tech-debt-tracker.md
  ├── generated/
  │   └── db-schema.md
  ├── product-specs/
  │   ├── index.md
  │   └── ...
  ├── references/
  │   ├── design-system-reference-llms.txt
  │   ├── nixpacks-llms.txt
  │   └── ...
  ├── DESIGN.md
  ├── FRONTEND.md
  ├── PLANS.md
  ├── PRODUCT_SENSE.md
  ├── QUALITY_SCORE.md
  ├── RELIABILITY.md
  └── SECURITY.md
  ```

- Design docs are **catalogued/indexed with a verification status** and a set of **core
  beliefs** (agent-first operating principles). `ARCHITECTURE.md` is the top-level map of
  domains + package layering. A **quality doc grades each domain/layer and tracks gaps**.
- **Plans are first-class**: ephemeral lightweight plans for small changes; complex work becomes
  an **execution plan** with progress + decision logs checked in. Active/completed/tech-debt are
  versioned and co-located so agents need no external context.
- This is **progressive disclosure**: a small, stable entry point that teaches where to look.
- Enforced **mechanically**: linters + CI validate the knowledge base is up-to-date,
  cross-linked, and structured; a recurring **"doc-gardening" agent** scans for stale docs and
  opens fix-up PRs.

### 5. Agent legibility is the goal
- The repo is optimized first for **Codex's legibility** — an agent should be able to reason
  about the **full business domain from the repo itself**.
- **"Anything it can't access in-context while running effectively doesn't exist."** Knowledge in
  Google Docs, chat threads, or people's heads is invisible; only **repo-local, versioned
  artifacts** (code, markdown, schemas, executable plans) count. Push context *into* the repo.
- Onboard the agent like a new teammate: product principles, engineering norms, team culture
  (even emoji preferences) → better-aligned output.
- Favor dependencies/abstractions that can be **fully internalized in-repo**. **"Boring"
  technologies** are easier for agents to model (composability, API stability, training-set
  presence). Sometimes it's cheaper to **reimplement a subset** than work around opaque upstream
  behavior — e.g. their own `map-with-concurrency` helper instead of a `p-limit`-style package:
  integrated with their OpenTelemetry, **100% test coverage**, exact runtime behavior.

### 6. Enforcing architecture and taste
- **Docs alone don't keep an agent-generated codebase coherent.** Enforce **invariants, not
  implementations** — e.g. require parsing data shapes **at the boundary**, without prescribing
  the library (the model gravitated to Zod on its own).
- Agents thrive with **strict boundaries + predictable structure**, so build a **rigid
  architectural model**: each business domain split into a fixed set of **layers** with strictly
  validated dependency directions and a limited set of permissible edges.
- The layering rule (example): within a domain, code depends **forward** through fixed layers
  **Types → Config → Repo → Service → Runtime → UI**. Cross-cutting concerns (auth, connectors,
  telemetry, feature flags) enter through a **single explicit `Providers` interface**. Anything
  else is disallowed and **enforced mechanically** (custom linters — Codex-generated — +
  structural tests).
- This is architecture you'd normally postpone until hundreds of engineers; **with agents it's
  an early prerequisite** — the constraints are what allow speed without decay/drift.
- Plus **"taste invariants"**: statically enforce structured logging, naming conventions for
  schemas/types, **file-size limits**, platform-specific reliability. Because lints are custom,
  their **error messages inject remediation instructions into agent context**.
- In a human workflow these feel pedantic; **with agents they're multipliers** — encoded once,
  applied everywhere at once. **Enforce boundaries centrally, allow autonomy locally.** Output
  need not match human style as long as it's **correct, maintainable, legible to future runs**.
- **Human taste is fed back continuously**: review comments, refactoring PRs, and user-facing
  bugs become doc updates or tooling. **"When documentation falls short, promote the rule into
  code."**

### 7. Throughput changes the merge philosophy
- High agent throughput makes many conventional norms counterproductive: **minimal blocking
  merge gates, short-lived PRs**, and treating **flaky tests with follow-up runs** rather than
  blocking indefinitely. Corrections are cheap, waiting is expensive. (Irresponsible at low
  throughput; often right here.)

### 8. What "agent-generated" actually means — *everything*
- Agents produce: product code + tests, CI config + release tooling, internal dev tools, docs +
  design history, **evaluation harnesses**, review comments + responses, **scripts that manage
  the repo itself**, and production dashboard definitions.
- Humans stay in the loop at a **different abstraction**: prioritize, translate feedback into
  acceptance criteria, validate outcomes. **When the agent struggles, treat it as a signal** —
  find what's missing (tools/guardrails/docs) and feed it back, **always by having Codex write
  the fix**. Agents pull feedback, respond inline, push, and often squash-merge their own PRs.

### 9. Increasing levels of autonomy
- With the dev loop encoded (testing, validation, review, feedback, recovery), the repo crossed
  a threshold where, from a **single prompt**, Codex can: validate current state → reproduce a
  bug → **record a video of the failure** → implement a fix → validate by driving the app →
  **record a second video of the resolution** → open a PR → respond to feedback → detect + fix
  build failures → **escalate to a human only when judgment is required** → merge.
- This **depends heavily on the repo's specific structure/tooling** and shouldn't be assumed to
  generalize without similar investment — *yet*.

### 10. Entropy and garbage collection
- Autonomy brings novel problems: **Codex replicates existing patterns — even uneven ones — so
  drift is inevitable.** Manual cleanup (a "Friday = 20% of the week cleaning AI slop") **didn't
  scale**.
- Instead, encode **"golden principles"** — opinionated, mechanical rules that keep the codebase
  legible/consistent for future runs. Examples: (1) **prefer shared utility packages over
  hand-rolled helpers** (centralize invariants); (2) **don't probe data "YOLO-style"** — validate
  boundaries or use typed SDKs so the agent can't build on guessed shapes.
- On a cadence, **background Codex tasks** scan for deviations, update quality grades, and open
  **targeted refactoring PRs** — most reviewable in **under a minute and automerged**.
- This is **garbage collection**. Tech debt is a **high-interest loan** — pay it down
  continuously in small increments rather than in painful bursts. **Human taste captured once,
  enforced continuously**; bad patterns caught daily, not after weeks.

### 11. What we're still learning
- Open questions: how architectural coherence holds over **years** in a fully agent-generated
  system; **where human judgment adds the most leverage** and how to encode it so it compounds;
  how the system evolves as models improve.
- The takeaway: **building software still demands discipline, but the discipline shows up in the
  scaffolding rather than the code** — the tooling, abstractions, and feedback loops that keep
  the codebase coherent. The hardest work is now **designing environments, feedback loops, and
  control systems** so agents can "just build things."

## The golden rules, distilled (a checklist)

1. **`AGENTS.md` is a ~100-line map, not an encyclopedia.** Link to the real source of truth.
2. **`docs/` is the system of record** — code that disagrees with it is a bug in one of them.
3. **Progressive disclosure** — small stable entry point → pointers to deeper docs.
4. **If the agent can't see it in-repo, it doesn't exist.** Push context in; kill tribal
   knowledge. Prefer versioned artifacts over chat/docs/heads.
5. **Enforce invariants mechanically, not implementations.** Rigid layers, validated dependency
   directions, single explicit interface for cross-cutting concerns.
6. **Taste invariants as lints** — structured logging, naming, file-size caps — with **error
   messages that tell the agent how to fix it**.
7. **Prefer boring, internalizable tech**; reimplement a small subset rather than fight opaque
   upstream behavior.
8. **Plans are first-class artifacts** (active / completed / tech-debt), versioned in-repo.
9. **A quality doc grades each domain/layer and tracks gaps over time.**
10. **Continuous garbage collection** — encode golden principles + recurring cleanup agents that
    open small, automergeable refactor PRs. Pay debt down daily.
11. **Merge philosophy scales with throughput** — short-lived PRs, minimal blocking gates, and
    follow-up runs for flaky tests rather than indefinite blocking. Corrections are cheap; waiting
    is expensive.
12. **When docs fall short, promote the rule into code.** When the agent struggles, add the
    missing capability — and have the agent write that fix too.
13. **Derived rule: write concise docs.** Context is scarce and every token competes with the
    task, so verbose, padded prose is a cost, not thoroughness. Say it once, link instead of
    repeating, cut hedging and filler. *Too much guidance becomes non-guidance* — resist the LLM
    tendency to over-explain.

### A starter `docs/` layout

```text
AGENTS.md                      # ~100-line map
ARCHITECTURE.md                # domains, layers, allowed dependency edges
docs/
├── README.md                  # optional adaptation: router for humans/tools
├── design-docs/
│   ├── index.md               # catalog + verification status (current/stale/superseded)
│   ├── core-beliefs.md        # agent-first operating principles
│   ├── conventions.md         # optional adaptation: commit / code / naming conventions
│   └── <dated design docs>.md
├── exec-plans/
│   ├── active/                # in-flight plans (decision logs)
│   ├── completed/             # shipped plans, kept for history
│   └── tech-debt-tracker.md   # known deferred work (id, severity, date)
├── generated/                 # machine-generated + verified references
├── product-specs/             # what it's for / who it serves
├── references/                # stack reference material, external notes
└── QUALITY_SCORE.md           # grades per domain/layer + tracked gaps
```

### Minimum viable harness (adapted starter order)

1. `AGENTS.md` map + `docs/` system of record. If you use multiple agents, keep them
   **tool-agnostic** by making one canonical source and having other tool-specific files import or
   point to it.
2. One command that runs the full gate (`make ci` or equivalent), mirrored exactly in CI.
3. Optional git hooks: **pre-commit** = fast drift scan, **pre-push** = full gate.
4. A **layer/dependency linter** so the pure core can't import upward — with a remediation
   message in the failure.
5. A **doc-drift gate**: key docs are cross-linked, structured, and checked for staleness.
6. Optional quality ratchets where they match the project: coverage, lint score, reliability
   checks, or domain/layer quality grades.
7. A scheduled drift/garbage-collection scan that surfaces or auto-fixes rot continuously.
8. A tech-debt tracker: log deferrals explicitly so they surface instead of rotting.
